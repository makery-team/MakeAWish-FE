# 1:1 실시간 채팅 연동 및 트러블슈팅 (WebSocket & JWT)

## 📌 배경 및 문제 상황
기존 앱 내에서는 사용자가 매장 사장님과 직접 소통할 수 있는 기능이 부족하여, 단순 문의나 주문 관련 세부 조율에 어려움이 있었습니다. 이를 해결하기 위해 **1:1 실시간 채팅 기능**을 도입하게 되었습니다. 

하지만 구현 과정에서 두 가지 큰 기술적 허들을 마주했습니다.

1. **보안 취약점 (인가 문제):**
   - 웹소켓(STOMP) 연결 시, 프론트엔드에서 단순히 유저 번호(`userId`)만 평문으로 실어 보내는 구조였습니다.
   - 누군가 악의적으로 다른 사람의 유저 번호를 입력하면 그 사람의 권한으로 채팅방에 접속할 수 있는 심각한 보안 취약점이 있었습니다.
2. **도메인 논리 불일치 (채팅 대상 식별 오류):**
   - 손님이 '매장'을 보고 채팅을 걸기 때문에 프론트엔드는 채팅방 생성 API에 `shopId(매장 번호)`를 보냈습니다.
   - 하지만 백엔드는 이를 `userId(상대방 유저 번호)`로 취급하여 검색했고, 매장 번호와 실제 사장님의 유저 번호가 일치하지 않아(또는 존재하지 않아) **500 Internal Server Error**가 발생하며 채팅방이 만들어지지 않았습니다.

## 🛠️ 해결 과정 (나의 기여)

### 1. 웹소켓 Handshake 단계의 JWT 인증 도입 (보안 강화)
안전한 통신을 위해 HTTP API에만 적용되던 JWT 토큰 인증 방식을 웹소켓에도 확장 적용했습니다.
- **프론트엔드(`useChatSocket.ts`)**: 소켓 연결을 시도할 때 `ws://...?token=JWT_TOKEN` 형태로 토큰을 포함하도록 수정했습니다.
- **백엔드(`CustomHandshakeInterceptor.java`)**: 소켓 Handshake(연결 수립) 단계에서 토큰을 가로채어 유효성을 검증(`TokenProvider.validateToken`)하고, 조작된 토큰이거나 만료된 토큰일 경우 연결을 원천 차단하도록 보안 로직을 구현했습니다.
- **결과**: 인가된 정상 유저만 채팅 서버에 접근할 수 있게 되어 서비스의 보안 신뢰성을 크게 향상시켰습니다.

### 2. 도메인 논리 재구조화 (Store ID ➡️ Seller User ID)
손님은 '매장'에게 말을 걸지만, 실제 메시지는 '매장 주인의 계정'으로 들어가야 하는 도메인 특성을 백엔드 로직에 반영했습니다.
- **프론트엔드**: 기존과 동일하게 매장 ID(`storeId`)를 보내도록 명확히 네이밍을 수정했습니다.
- **백엔드(`ChatRoomController.java`)**: 채팅방을 생성할 때, 받은 `storeId`로 먼저 `StoreRepository`를 조회하고, 매장과 1:1로 매핑된 `SellerProfile`을 거쳐 **실제 사장님의 유저 정보(User)**를 추출하도록 구조를 개선했습니다.
- **결과**: 어떤 목업 매장이나 신규 매장이더라도 예외 없이 실제 주인(사장님) 계정과 정확하게 1:1 채팅방이 연결되도록 결함을 완벽히 해결했습니다.

### 3. 사용자 경험(UX) 고도화
- 백엔드 응답(`ChatRoomWithMessagesDto`)에 상대방의 실제 닉네임(`otherName`) 필드를 추가하여, 프론트엔드 채팅 목록에서 직관적으로 상대방을 식별할 수 있도록 개선했습니다.

### 4. 프론트엔드 - 백엔드 통신 규격 일치화 (Content-Type)
- **문제**: 채팅방 생성 API 호출 시, 백엔드 로직이 정상적임에도 불구하고 계속해서 동일한 에러 로그가 출력되었습니다.
- **해결**: 프론트엔드의 `fetch` API 호출 시 `Content-Type: application/json` 헤더가 누락되어, 백엔드의 `@RequestBody`가 이를 `415 Unsupported Media Type`으로 거부하고 있었습니다. 헤더를 명시적으로 추가하여 통신 규격을 완벽히 맞추었습니다.

### 5. 화면 생명주기(Lifecycle)를 고려한 상태 동기화 및 기록 보존
- **문제**: 채팅을 생성하거나 이전 대화를 나눈 후 뒤로 가기를 눌렀을 때, 채팅방 목록이나 과거 대화가 보이지 않는 현상이 있었습니다.
- **해결**: 
  1. **채팅방 목록**: Expo Router의 탭 구조에서 `useEffect` 대신 `useFocusEffect`를 사용하여, 탭 화면이 포커스될 때마다 목록 API를 재호출하도록 하여 최신 상태를 유지하게 했습니다.
  2. **과거 대화 조회**: 백엔드에 누락되어 있던 과거 메시지 내역 조회 API(`GET /chatting/rooms/{roomNumber}/messages`)를 추가 구현하여, 채팅방 재입장 시 기존 대화를 완벽하게 불러오도록 수정했습니다.
  3. **UX 개선**: 채팅방 최상단에 `ListHeaderComponent`를 활용하여 안전 거래 권고 공지사항을 고정 노출했습니다.

### 6. 다대다 채팅방 구조에서의 기준점(Perspective) 오류 해결
- **문제**: 채팅방 목록이나 과거 대화에서 내가 보낸 메시지가 상대방이 보낸 것으로 뜨고, 상대방 이름이 내 이름으로 뜨는 등 '나'와 '상대방'이 완전히 뒤바뀌어 보이는 심각한 논리 오류가 발생했습니다.
- **원인**: 백엔드에서 중복 채팅방 생성을 막기 위해 항상 ID가 작은 사람을 `user`, 큰 사람을 `other`로 강제 고정하여 DB에 저장하고 있었습니다. 그런데 채팅 내역을 내려줄 때 API를 호출한 당사자(요청자)가 누구인지 고려하지 않고 무조건 DB의 `user`를 나로, `other`를 상대방으로 취급해 반환했기 때문이었습니다.
- **해결**: 
  - 백엔드 DTO(`ChatRoomWithMessagesDto`)의 생성자 파라미터에 `requestUserId`(API 요청자 ID)를 추가로 받도록 수정했습니다.
  - `requestUserId`와 DB의 `user.id`를 비교하여, 요청자가 1번 유저인지 2번 유저인지 동적으로 판별한 뒤 `userId`와 `otherId`, `otherName`을 정확하게 매핑하도록 백엔드 로직을 전면 재구축했습니다.

## 💡 성과 및 배운 점
프론트엔드와 백엔드를 아우르는 데이터의 흐름(Data Flow)을 이해하고, 단순히 에러를 덮는 것이 아니라 **도메인의 논리적 연결 구조(Store ➡️ Seller ➡️ User)를 파악해 근본적인 원인을 해결**하는 경험을 했습니다. 

특히 웹소켓이라는 지속적인 연결 상태에서도 HTTP와 동일한 수준의 보안(JWT)을 적용하는 방법을 고민하고 구현함으로써, 안전한 실시간 서비스 구축에 대한 자신감을 얻었습니다.
